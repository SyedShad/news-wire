# News Wire 0.6.0 staged rollout

This is a rollout procedure, not a deployment record. Production access, data,
credentials and publication have not been changed. Complete local real runs,
then isolated hosted acceptance, then production rollout.

An initial compatibility deployment may deliver the new hosted layout while
`GENERATION_ENABLED=false`. It retains every cached bridge-2.2 record across all
history, uses detection time where old rows lack a fetch timestamp, opens legacy
story IDs through their retained source/history route, and shows clearly disabled
generation sections. Unsupported article/catalog reads are not queued to the old
bridge. No Mac database upgrade or inference is required for this first layout
delivery. Real inference activation still follows the acceptance sequence below.

## 1. Local acceptance before deployment

Finish the application's Sign in with ChatGPT flow and check `generation status`
using the new checkout CLI and the same configured authentication root. This
status path does not migrate the database. Never print or copy credential JSON.

Run the new local dashboard against a dedicated test data root, with a small
explicitly selected article fixture. Supply the existing protected
`ChatGPTPlanAuth` object to `GenerationService` for test execution; do not put
credentials in fixtures, archives, environment files or hosted runtime values.
Do not seed production notification destinations or run collection during this
test. Preserve all production processes and configuration.

Complete one real text job and one graphics job using the available runtime
models and installed skills. Verify independent selections, ordered skills,
customizations, interactive replies, cancellation, retry, immutable edited
versions, copying, Markdown download, graphics preview/download and restart
recovery. Confirm a model-access failure preserves inputs and prior output.
Graphics must produce a real downloadable artifact. Catalog discovery and
sign-in status alone do not establish generation readiness.

Finish runtime protocol tightening and its checks before freezing the source.
Record actual outcomes. Keep native image-generation limitations visible and
do not introduce a paid fallback.

## 2. Isolated hosted acceptance

Local Vinext preview uses a separate local D1 database. It is useful for UI and
migration checks but cannot prove real hosted relay or artifact transport.
The callable Sites deployment operations publish real hosted versions; there
is no exposed isolated hosted-preview operation. Therefore use a separate
owner-private staging Site for cross-device and bridge acceptance.

1. Register a separate staging Site only when that step is authorized. Copy its
   returned project ID exactly into the staging source manifest. Declare
   `d1: "DB"`; Sites provisions storage for that Site. Do not reuse the
   production project ID, production D1 binding identity or production secrets.
2. Set the staging `AUTH_BASE_URL` to its actual returned origin and configure
   independent owner-session/verifier and bridge secrets. Keep push delivery
   disabled. Store staging machine-access and bridge credentials only in the
   Mac Keychain for the staging origin, through protected standard input.
   Confirm staging and production databases are distinct before any writes.
3. Open the staging source using the Sites source helper. Copy the reviewed
   candidate into that checkout, assign the real staging identity, and run the
   required checks/build. The helper must push the exact source commit before
   it packages a deployment archive. Pass the resulting project ID, commit SHA
   and unchanged archive to Sites. Do not opt into automatic publish-on-push.
4. Publish privately to staging after local acceptance. Sites applies pending
   hosted migrations before Worker upload; verify migration 0007 and existing
   history/read-request preservation. A failed deployment may already have
   applied migrations, so inspect its state before retrying.
5. Run an isolated foreground Mac bridge using the test data root and the
   existing protected auth object injected into its generation service. Do not
   install a staging LaunchAgent: bridge, scanner and Telegram labels are
   global per-user and would replace production services. Do not reconfigure
   the production data root's hosted origin.
6. Verify unauthenticated denial, owner access, bridge 2.3.0 and a moving
   heartbeat. Run a harmless `bridge.healthcheck`, then one selected text job
   and one graphics job from the hosted article page. Verify command/result
   transitions, interactive input, cancellation/retry, edited versions and
   authenticated artifact download. Check byte count/SHA256, bounded chunks,
   missing-chunk handling, unsafe-format attachment behavior and access denial
   without an owner session. Keep publishing manual.

Keep the successful staging version and evidence. Stop its owned foreground
bridge after acceptance. No production generation is needed for this phase.

## 3. Immutable Mac upgrade and production rollout

The feed and local workspace upgrade may proceed before inference acceptance,
after a successful history migration rehearsal and consistent live backup.
Keep hosted generation disabled until both acceptance phases succeed.
Freeze a reviewed, tested source commit. The normal
installer requires a clean commit reachable from owner `origin/main` and a
JSON validation report bound to that exact SHA, with successful `full_tests`,
`coverage_gate`, `dependency_audit` and `sast` records. Do not manufacture a
passing report or use an audited override for an ordinary production upgrade.

Before mutation, record the current stable launcher target and each service's
loaded/running state. Stop the hosted bridge, pause the scanner, stop open local
dashboards and temporarily unload the Telegram LaunchAgent if loaded. Preserve
its configured enabled state rather than disabling/unpairing its destination.
Wait for active database writers and generation to stop.

Create a consistent SQLite backup with the SQLite backup API, validate its
integrity, and keep it owner-readable with the previous release and private
config/files required for recovery. Do not copy a live database file without
accounting for WAL contents. No installer-created backup exists.

Install with the reviewed new CLI:

```text
open-source-ai-news-wire --data-root <existing-runtime-data-root> app install --source-root <reviewed-clean-checkout> --validation-report <exact-commit-report.json>
```

The installer builds a pinned immutable release under
`~/.local/share/open-source-ai-news-wire/releases/0.6.0-<source-digest>`, verifies
it, runs its explicit schema-11 migration, then atomically switches
`~/.local/bin/open-source-ai-news-wire` through the stable `current` pointer.
Verify schema, retained articles/drafts/notification ledgers, installed app
version and bridge 2.3.0 before restarting anything.

Retain the existing runtime data root and production hosted origin. Installation
does not replace `config/hosted-bridge.json`, the application's protected
`config/chatgpt-plan.json`, or origin-keyed macOS Keychain bridge/Sites entries.
Do not reconfigure, rotate or package them merely to upgrade. The existing
LaunchAgent points at the stable launcher and needs a restart, not a new
production origin. Use `hosted-bridge once` only after the hosted upgrade below.

Prepare/push the tested production hosted source through the Sites helper,
preserving its current project ID and owner-only access. Retain version 12 and
publish the exact archive/commit that passed staging. Verify migration 0007,
unauthenticated denial and owner access before allowing a bridge sync.

Run one signed synchronization and harmless healthcheck, then restart the
existing bridge (`hosted-bridge start`) and restore only the previously active
scanner/Telegram processes. Verify a moving heartbeat and operational counts.
Run the selected production acceptance jobs after local and staging acceptance
succeeds, and keep publication manual.

## Rollback

A Sites rollback can redeploy saved version 12 while retaining the additive
hosted schema changes; it does not roll back the Mac database. Inspect uncertain
deployment/migration state before replaying any action.

The installed 0.5.2 release uses schema 10 and cannot run against migrated schema
11. Merely switching its launcher back is insufficient. Stop writers and
deliveries, preserve post-upgrade output and notification records, restore the
consistent schema-10 backup, then switch to the retained release and verify its
schema before restarting. Keep external deliveries stopped until any ledger
changes since the backup are reconciled to avoid replaying delivered alerts.
An authorized database restore is a separate operation; do not perform it as an
automatic response to a failed check.
